# PVArr 0.18.0

Everything in [0.17.0](v0.17.0.md), plus:

- **An optional browser sidecar for links whose player builds its playlist in JavaScript.** Those
  links used to show up as "unresolved" in Find and on the recording card, and on some event pages
  they include the only healthy feed. The new `pvarr-browser` container opens such a page in
  headless Chromium, starts the player the way a viewer would, and reports the playlist it
  requested. With `PVARR_BROWSER_URL` set, PVArr asks it about exactly those links (never about a
  dead playlist or a 404):
  - **Find, scheduled scans, the event-page re-check:** only when the probe came up short (fewer
    than three working links, or all one source). Up to 4 links, one at a time, 45 s at most;
    one it resolves is logged `found by the browser sidecar` and ranked like any other.
  - **Connect and failover:** such a link is resolved again each time (playlist tokens expire),
    7-10 s when it works.
  - PVArr's own probe still checks every playlist the sidecar returns before using it.
  On live event pages it turned 1-4 unresolved links per game into recordable new sources.

**Cost:** 0.3-0.9 GB of RAM and about one CPU core per open page, for 7-35 s; about 250 MB idle.
The image is about 1.8 GB.

**Security:** the sidecar runs untrusted page JavaScript with Chromium's sandbox off, so it must be
network-isolated. Use the Compose example in [docs/browser-sidecar.md](../browser-sidecar.md)
unchanged (holder container, internal network, no published port) and add the host firewall rule.

**Upgrading:** `docker compose pull && docker compose up -d`, ideally while nothing is recording.
No settings change; the sidecar is off until you add it and set `PVARR_BROWSER_URL`.
